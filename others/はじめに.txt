【文書情報】
文書名: Guild of Merchants 開発開始・引継運用ルール
最終更新: 2026-11-22
文字コード: UTF-8（BOMなしを推奨）
対象: Godot 4.3 / GDScript / GitHub
リポジトリ: https://github.com/endbreakgt-jpg/guild-of-merchants

【この文書の位置づけ】
本書は「作業の進め方」を定める運用ルールであり、ゲーム仕様ではない。
- others/引継.txt: 現在の方針、実装状態、直近タスク
- others/00_Guild_of_Merchants_憲法_v1.0_2026-03-16.txt: ゲーム設計の最上位原則
- others/README.md: その他資料の案内、配置方針
- others/specs/: 仕様・設計資料（作成時点の内容。現在のコードと相違する場合がある）
- others/reference/: 世界観や経済などの参考資料・構想
- others/archive/: 完了済み差分・作業ログなどの履歴資料

【原則と参照順序】
1. ユーザーが現在のチャットに提示した最新コード／明示した条件
2. GitHubの対象ブランチの最新コミット済みコード
3. others/引継.txt（現行方針・確認済み範囲）
4. 本書（開発運用）
5. 憲法、個別仕様書、参考資料、履歴資料
※ ゲーム設計の優先原則は憲法による。コードの実体確認は対象ブランチに基づく。
※ 仕様書に記載があっても、実装・動作確認済みと見なさない。
※ 作業開始時は、はじめに.txt → 引継.txt → 対象コード・関連仕様を直接確認する。
※ mainと作業ブランチ、ユーザーのローカル差分が食い違う場合は、勝手に上書き・混合せず差分を明確にする。

【標準フロー：相談からマージまで】
1. 相談・調査・実装計画
   - 方針や不明点を整理し、ユーザーの計画承認を得る。
   - 計画承認前のGitHub更新は行わない。
2. 仕様書作成
   - 承認された計画を基に、必要な仕様書を作業ブランチへ配置する。
   - 仕様が曖昧で実装結果に影響する場合、分岐案を明示して確認する。
   - 仕様の追加承認を求められた案件では、実装前にその承認を得る。
3. 作業ブランチで実装
   - 最新のmainを基準として feature/...、fix/...、docs/... 等のブランチを作成。
   - 変更対象を確認して実コードを編集し、ブランチにコミットする。
   - 差分TXTの手動適用・ZIP配布は標準手順としない。
4. 検証とPR
   - 実行可能な検証だけを実施。実施済み／未実施／失敗を明確にする。
   - PRに変更理由、仕様書、主要差分、検証結果、既知の制約、確認項目を記載する。
   - 影響が大きい場合は仕様書と実装を別コミットにする。
5. ユーザー確認
   - PRやVS Codeで差分を確認し、ローカルのGodot 4.3で実画面検証する。
   - NGがあれば同じ作業ブランチに修正コミットし、PRを更新する。
6. mainへのマージ
   - mainへのマージは、ユーザーが明示的に承認／依頼した場合に限る。
   - mainへの直接コミットも、ユーザーの明示的な指定がある場合だけ例外として許可する。
   - GitHubにコミットしただけでGodotの実画面確認が完了したとは扱わない。

【承認範囲】
- 調査、読み取り、計画の提案はGitHubを変更せず実施できる。
- 「計画承認・実装依頼」は、原則として作業ブランチの作成、仕様書・コード変更、
  コミット、PR作成・更新までを許可する。mainマージは含まない。
- 文書・資料整理の明示的依頼も、作業ブランチとPRで扱う。
- 既存コードの破壊的変更、範囲外の追加機能、データ削除、外部公開等は別途確認する。
- ローカル未コミット変更は、GitHub連携からは見えない。ユーザーから提示された差分を優先する。

【実装上のルール】
- Godot 4.3/GDScriptを基準とし、インデントはスペースで統一する。
- Godotで使えない「? :」形式の三項演算子を生成しない。
- 役割分担: world.gd=状態・経済・日次処理、game_hud.gd=UI母艦、
  menu_panel.gd=補助UI、map_layer.gd=MAP描画・入力、story.gd=物語進行。
- 修正報告では関数単位で変更箇所を列挙する。1000行超のスクリプトもGitHub上では
  通常どおり編集できる（チャットで全文配布する際のみ関数差分を優先する）。
- UI変更はCITY / MAP / DIALOG / WINDOWの責務と入力制御を先に確認する。
- GitHub経由の編集が使えない場合は、例外として関数単位の差分TXT、
  必要に応じて1000行以下の完成TXT、適用手順を返す。

【テスト・結果共有】
- 実装・UI・セーブデータ・設定値の変更には原則としてテスト項目を用意する。
- PR内または others/tests/ のテスト資料に、適用コミットSHA、変更対象、
  前提、操作、期待結果、実際の結果を記す。
- 番号: A-01、A-02、B-01等。追加時は既存番号を維持する。
- 結果区分: OK / NG / 未実施 / 対象外。テストできない環境では未実施を明記する。
- 最低限: 起動・構文解析、主経路、閉じる／戻る／再操作、周辺回帰、保存・復元。
- UIウィンドウは開閉を3回程度繰り返して排他・フォーカスを確認。
- エラー時はDebug全文・直前操作・スクリーンショット・可能なら行動ログを共有する。
- 行動ログはHUDのEXPからTXT出力できる。個人情報を含むパスは必要に応じて伏せる。
- テスト資料名は gom_<テーマ>_test_YYYY-MM-DD.txt を基本とする。

【資料配置と保守】
- others直下は入口（はじめに、引継、憲法、索引）とGodotが参照し得る素材に限定する。
- 現行の設計・仕様資料は others/specs/。参考案は others/reference/。
- 完了済みパッチ・単発ログ・旧案は others/archive/ に保管し、原則として再適用しない。
- 試験・検証手順は others/tests/。プロジェクトの稼働コードと区別する。
- ファイル移動時はコード／シーンのres://参照、関連import設定、資料間参照を確認する。
- バイナリ素材など参照のあるリソースは整理だけを理由に動かさない。
- 既存の履歴資料は削除せず移動で整理する。アーカイブは現行仕様の根拠にしない。
- 引継.txtは履歴台帳ではない。現行方針、実装、次タスク、運用注意に絞り、
  150行前後を超えたら圧縮を検討する。
- 変更後にothers/README.mdと関連参照先を更新する。
