【引継資料運用ルール】

[githubリポジトリURL]
https://github.com/endbreakgt-jpg/guild-of-merchants

・引継資料（例: others/引継.txt）は、作業履歴の蓄積ではなく「現在有効な前提を共有するための資料」として扱う。
・追記を続けて肥大化させるのではなく、節ごとに上書き更新して圧縮することを基本とする。
・引継資料には、原則として以下のみを残す。
  1. 現在の確定方針
  2. 現在の実装状態
  3. 次タスク
  4. 実装運用メモ
・完了済みで今後の設計判断に影響しない詳細ログ、単発の検証メモ、過去の試行錯誤の細部は引継資料から削除する。
・詳細な履歴を残したい場合は、引継資料に蓄積せず、別ファイル（例: others/archive/引継_YYYY-MM.txt）へ退避する。
・引継資料が長くなった場合の目安として、150行前後を超えたら圧縮を検討する。
・直近3テーマ以外の完了済みログは、必要なら1〜2行に要約して残す。
・引継資料は VS Code 側で参照しやすいことを優先し、見出し・改行・箇条書きを用いて可読性を保つ。
・新規チャット用の引継サマリを作成する際も、最新状態を短く整理し、次に着手すべき内容がすぐ分かる形にする。
・毎回の会話後は、全文追記ではなく「現在の確定方針」「現在の実装状態」「次タスク」「実装運用メモ」を更新する意識で整理する。
・コード修正の引継では、完成ファイルよりも関数差分・パッチ・置換単位の説明を優先し、次の作業者が安全に差分適用できるようにする。
・引継資料には、数値調整中の暫定値を細かく残しすぎず、「何が仮で、何が確定か」が分かるように記載する。
・今後の会話でも、引継資料が肥大化してきた場合は、必要に応じて内容の圧縮版を提案し、整理した形で更新する。

【GitHub参照運用】
・ソースコード確認は、原則として GitHub リポジトリのコミット済み内容を参照する。
・現在の方針、実装状態、次タスクは others/引継.txt を確認する。
・world.gd を状態管理の中枢、game_hud.gd を UI の母艦、menu_panel.gd を補助 UI、map_layer.gd を地図操作、story.gd を会話と状態遷移の接着剤として扱う。
・GitHub 上にコード断片が存在しても、UI や運用まで完成しているとは限らないため、引継.txt とロードマップで未完了事項を確認する。
・GitHub 参照時は、ディレクトリ一覧や断片的な検索結果だけで判断せず、必要ファイルを直接パス指定で確認する。
・会話開始時は、原則として最低限以下を直接確認する。
  1. はじめに.txt
  2. others/引継.txt
  3. 今回の主対象ファイル（例: scripts/world.gd, ui/game_hud.gd など）
・GitHub 上の内容とユーザー報告が矛盾する場合は、未コミットのローカル差分の可能性を考慮し、ユーザー報告を優先する。
・修正提案は、完成ファイルよりも関数差分・パッチ・置換単位を優先する。
・引継資料は追記で肥大化させず、節ごとに上書き更新して圧縮する。

【参照優先順位】
・情報の優先順位は以下の通り。
  1. ユーザーがチャットに貼った最新コード
  2. GitHub の最新コミット済みコード
  3. others/引継.txt
  4. はじめに.txt
  5. 体験版ロードマップ / 各仕様書 / 相関図資料 / 旧メモ
・現在の方針、実装状態、次タスクは others/引継.txt を正とする。
・ソースコードの実体確認は GitHub を正とする。
・資料間で差異がある場合は、古い仕様書より最新コードと引継内容を優先する。
・「コード上に断片がある」ことと「UIや運用まで完成している」ことは同義ではないため、未完了事項は引継.txt とロードマップで再確認する。

【会話開始時の確認事項】
・今回触る対象が world.gd / game_hud.gd / menu_panel.gd / map_layer.gd / story.gd のどこかを先に確認する。
・修正対象が CITY / MAP / DIALOG / WINDOW のどのモードに属するかを整理してから着手する。
・既存の責務分担を崩さないことを優先する。
  - world.gd = 状態管理の中枢
  - game_hud.gd = UI の母艦
  - menu_panel.gd = 補助 UI
  - map_layer.gd = 地図 / 経路系
  - story.gd = 会話と状態遷移の接着

【返却形式】
・1000行を超える長いスクリプトは完成ファイルではなく、関数差分・置換単位・パッチ形式を優先する。
・差分提示時は、できるだけ「変数追加」「既存関数置換」「新規関数追加」「呼び出し箇所追記」を分けて示す。
・UI 調整は対象関数または対象ブロックを丸ごと置換する形を優先する。
・提案時は、変更内容だけでなく「どの責務に属する修正か」「暫定仕様か確定仕様か」を短く明記する。
・GitHub 参照で確認した修正については、可能なら参照したファイルまたは更新済みである旨を残す。
・VS Code 側に変更意図が伝わるようにヘッダーに情報を記載の上、テキストファイルで出力する。

【テスト項目の作成・返却ルール】
・コード、UI、セーブデータ、設定値を変更する返却物には、原則としてテスト項目を付ける。
・テスト表には、対象コミットSHA、変更対象ファイル、前提条件、適用方法、期待結果を記載する。
・テスト項目はテーマ別に A / B / C、項目ごとに A-01 / A-02 のような固定番号を付ける。
・追加テストを後から依頼する場合も既存番号は変更せず、末尾へ A-03 のように追加する。
・項目を廃止する場合は番号を詰めず、「対象外」として理由を残す。
・各項目の結果は「OK / NG / 未実施 / 対象外」の4種類で共有する。
・各テストは「操作」と「期待結果」を分け、判定基準を曖昧にしない。
・最低限、以下の観点を含める。
  1. 起動・構文解析・初期表示
  2. 修正した主経路
  3. 閉じる・戻る・キャンセル・再押下・連続実行
  4. 隣接機能の回帰確認
  5. 状態を持つ変更ではセーブ・ロード
  6. 出力機能を持つ変更ではファイル生成と内容確認
・ウィンドウやダイアログの修正では、開閉を3回程度繰り返し、排他ウィンドウ、フォーカス、親子関係のエラーが出ないことを確認する。
・トグルUIは「表示 → 非表示 → 再表示」を一組として確認する。
・テスト表のファイル名は、原則として gom_<テーマ>_test_YYYY-MM-DD.txt のASCII名を使う。

【テスト結果の共有テンプレート】
・結果共有は、次の形式を基本とする。
  TEST-ID / パッチ名:
  適用元コミットSHA:
  Godotバージョン:
  実行環境:
  セーブデータまたは開始状態:
  結果一覧: A-01 OK / A-02 NG / B-01 未実施
  NG項目番号:
  直前の操作:
  期待した結果:
  実際の結果:
  Godot Debuggerエラー全文:
  行動ログのファイル名:
  スクリーンショット:
・NGが複数ある場合は、NG項目番号ごとに「直前の操作」以下を分ける。
・エラーは要約だけでなく、先頭行、C++ソース、スタックトレースを含む全文を共有する。
・再現しない場合も「再現せず」と、試行回数を記載する。

【行動ログ・障害報告の運用】
・行動ログ対応版では、上部の EXP ボタンから action_log_*.txt を出力し、動作結果の共有に使用する。
・行動ログにはゲーム内日時、Day、ターン、現在地、所持金、積載量、信用、直近の行動を含める。
・不具合報告時は、可能であれば action_log_*.txt、Debuggerエラー全文、該当画面のスクリーンショットをセットで共有する。
・ログだけで再現条件が分からない場合があるため、該当テスト番号と直前の操作を必ず添える。
・個人情報やOSユーザー名を含むパスは、共有前に必要に応じて伏せる。

【成果物の配布・適用ルール】
・ブラウザから取得しやすいよう、返却物は原則としてASCII名のZIPにまとめる。
・ZIPには最低限、適用用パッチとテスト項目ファイルを同梱する。
・1000行以下で完成ファイル返却が適切な場合は、更新済みファイルも同梱してよい。
・パッチには適用元コミットSHAを明記し、可能なら git apply --check を確認してから返却する。
・ユーザーから適用完了の報告があるまでは、返却パッチを「ローカル適用済み」とみなさない。
・GitHubへのコミット、push、PR作成は、ユーザーから明示的な依頼がある場合のみ行う。

【実作業の承認範囲】
・調査、ソース確認、原因分析、計画作成は、承認前でも読み取り作業として実施してよい。
・コード変更、ファイル更新、パッチ作成などの実作業は、ユーザーの承認後に行う。
・ユーザーが「修正してください」「更新をお願いします」など実作業を直接依頼した場合は、その依頼を対象範囲の承認として扱う。
・承認された範囲を超える仕様変更、外部公開、GitHub更新は別途確認する。

【憲法参照・運用ルール】
・設計判断に迷った場合は、個別仕様より先に「Guild of Merchants 憲法」を参照する。
・憲法は「何を主役にするか」「何を優先するか」を定める資料であり、数値・UI・個別機能の詳細は各仕様書で扱う。
・憲法と個別仕様が衝突した場合は、まず憲法を優先し、必要なら仕様書側を修正する。
・ただし、開発の進行により作品の重心そのものが変わった場合は、仕様書側で無理に吸収せず、憲法の見直しを検討する。
・後発アイデアは直ちに採用または却下せず、原則として「補強 / 実験 / 例外 / 改憲候補 / 却下」のいずれかで扱う。
・単発の思いつきは、原則としてまず「実験」として扱う。
・後発アイデアの記録は1行メモで残す。
・1行メモの書式は「日付 | 分類 | 要素名 | ねらい | 懸念 | 扱い」を基本とする。
・複数回にわたり必要性が生じ、かつ作品の核を更新する必要がある場合のみ「改憲候補」を検討する。
・憲法そのものを肥大化させないため、記録ルールや運用メモは憲法ではなく本ファイル側で管理する。
