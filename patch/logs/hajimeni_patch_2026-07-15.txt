+【テスト項目の作成・返却ルール】
+・コード、UI、セーブデータ、設定値を変更する返却物には、原則としてテスト項目を付ける。
+・テスト表には、対象コミットSHA、変更対象ファイル、前提条件、適用方法、期待結果を記載する。
+・テスト項目はテーマ別に A / B / C、項目ごとに A-01 / A-02 のような固定番号を付ける。
+・追加テストを後から依頼する場合も既存番号は変更せず、末尾へ A-03 のように追加する。
+・項目を廃止する場合は番号を詰めず、「対象外」として理由を残す。
+・各項目の結果は「OK / NG / 未実施 / 対象外」の4種類で共有する。
+・各テストは「操作」と「期待結果」を分け、判定基準を曖昧にしない。
+・最低限、以下の観点を含める。
+  1. 起動・構文解析・初期表示
+  2. 修正した主経路
+  3. 閉じる・戻る・キャンセル・再押下・連続実行
+  4. 隣接機能の回帰確認
+  5. 状態を持つ変更ではセーブ・ロード
+  6. 出力機能を持つ変更ではファイル生成と内容確認
+・ウィンドウやダイアログの修正では、開閉を3回程度繰り返し、排他ウィンドウ、フォーカス、親子関係のエラーが出ないことを確認する。
+・トグルUIは「表示 → 非表示 → 再表示」を一組として確認する。
+・テスト表のファイル名は、原則として gom_<テーマ>_test_YYYY-MM-DD.txt のASCII名を使う。
+
+【テスト結果の共有テンプレート】
+・結果共有は、次の形式を基本とする。
+  TEST-ID / パッチ名:
+  適用元コミットSHA:
+  Godotバージョン:
+  実行環境:
+  セーブデータまたは開始状態:
+  結果一覧: A-01 OK / A-02 NG / B-01 未実施
+  NG項目番号:
+  直前の操作:
+  期待した結果:
+  実際の結果:
+  Godot Debuggerエラー全文:
+  行動ログのファイル名:
+  スクリーンショット:
+・NGが複数ある場合は、NG項目番号ごとに「直前の操作」以下を分ける。
+・エラーは要約だけでなく、先頭行、C++ソース、スタックトレースを含む全文を共有する。
+・再現しない場合も「再現せず」と、試行回数を記載する。
+
+【行動ログ・障害報告の運用】
+・行動ログ対応版では、上部の EXP ボタンから action_log_*.txt を出力し、動作結果の共有に使用する。
+・行動ログにはゲーム内日時、Day、ターン、現在地、所持金、積載量、信用、直近の行動を含める。
+・不具合報告時は、可能であれば action_log_*.txt、Debuggerエラー全文、該当画面のスクリーンショットをセットで共有する。
+・ログだけで再現条件が分からない場合があるため、該当テスト番号と直前の操作を必ず添える。
+・個人情報やOSユーザー名を含むパスは、共有前に必要に応じて伏せる。
+
+【成果物の配布・適用ルール】
+・ブラウザから取得しやすいよう、返却物は原則としてASCII名のZIPにまとめる。
+・ZIPには最低限、適用用パッチとテスト項目ファイルを同梱する。
+・1000行以下で完成ファイル返却が適切な場合は、更新済みファイルも同梱してよい。
+・パッチには適用元コミットSHAを明記し、可能なら git apply --check を確認してから返却する。
+・ユーザーから適用完了の報告があるまでは、返却パッチを「ローカル適用済み」とみなさない。
+・GitHubへのコミット、push、PR作成は、ユーザーから明示的な依頼がある場合のみ行う。
+
+【実作業の承認範囲】
+・調査、ソース確認、原因分析、計画作成は、承認前でも読み取り作業として実施してよい。
+・コード変更、ファイル更新、パッチ作成などの実作業は、ユーザーの承認後に行う。
+・ユーザーが「修正してください」「更新をお願いします」など実作業を直接依頼した場合は、その依頼を対象範囲の承認として扱う。
+・承認された範囲を超える仕様変更、外部公開、GitHub更新は別途確認する。
+
 【憲法参照・運用ルール】
 ・設計判断に迷った場合は、個別仕様より先に「Guild of Merchants 憲法」を参照する。
